# Spec NNN — Nombre de la funcionalidad

## Estado

Borrador / Pendiente de aprobación / Aprobada / En implementación / Verificada / Archivada.

## Contexto y objetivo

Qué problema resuelve la funcionalidad, por qué es importante y qué resultado se espera obtener.

## Usuarios / actores

Quién interactúa con la funcionalidad o se ve afectado por ella.

## Historias de usuario

- H1: Como [rol], quiero [acción] para [beneficio].

## Requisitos funcionales (criterios de aceptación en EARS)

- RF-1: [Ubicuo] EL SISTEMA hará [descripción verificable].
- RF-2: [Evento] CUANDO [evento], EL SISTEMA hará [descripción verificable].
- RF-3: [Estado] MIENTRAS [condición], EL SISTEMA hará [descripción verificable].
- RF-4: [Opcional] DONDE [condición], EL SISTEMA hará [descripción verificable].
- RF-5: [Error] SI [condición], ENTONCES EL SISTEMA hará [descripción verificable].

Los ejemplos anteriores son orientativos. Deben sustituirse por requisitos específicos, y solo deben utilizarse los patrones que correspondan.

## Requisitos no funcionales

Incluir únicamente requisitos aplicables, medibles y justificados.

Ejemplos orientativos:

- RNF-1: El tiempo de respuesta para una operación definida no superará el umbral acordado en las condiciones de prueba especificadas.
- RNF-2: La disponibilidad de un servicio cumplirá el objetivo acordado durante el período de medición definido.
- RNF-3: La información presentada respetará el formato y las reglas de validación acordados.

No incorporar cifras, umbrales ni compromisos que el usuario no haya aprobado o que no estén justificados por una norma o decisión aplicable.

## Casos límite

Describir los casos pertinentes para la funcionalidad, como:

- Valores vacíos o datos incompletos.
- Duplicados.
- Límites máximos y mínimos.
- Errores de conexión.
- Información desactualizada.
- Fuentes de datos no disponibles.
- Conflictos entre estados.
- Cancelación o interrupción de operaciones.

No asumir que todos los casos son aplicables. Identificar las dudas relevantes que deban resolverse.

## Fuera de alcance

Enumerar explícitamente las funcionalidades, comportamientos o escenarios excluidos de esta iteración.

## Criterios de finalización

Definir condiciones verificables para considerar terminada la funcionalidad, incluyendo el cumplimiento de los requisitos aplicables, las pruebas necesarias y la documentación pertinente.

## Dependencias y referencias

Identificar las especificaciones, decisiones o reglas del proyecto de las que depende esta funcionalidad.

No introducir detalles de implementación en esta sección.
